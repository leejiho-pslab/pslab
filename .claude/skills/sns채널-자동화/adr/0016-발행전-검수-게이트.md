# ADR-0016: 발행 전 검수는 수정요청 이슈를 게이트로 자동 발행에 물린다

- **상태**: 채택됨 (허브 + vittz 전용 인스턴스 배포 완료)
- **날짜**: 2026-08-01
- **관련 SKILL**: docs/05-발행-스케줄링.md · docs/06-대시보드.md §7
- **관련 ADR**: ADR-0007(대시보드 이스케이프), ADR-0012(문서 재편)

## 맥락 (Context)
수정요청 게시판(깃허브 이슈)과 자동 발행(`publish-plan --due`)이 **서로 모르는 채** 따로 돌았다.
운영자가 발행 전 콘텐츠에 수정요청을 남겨도 예정시각이 되면 수정 반영 여부와 무관하게 그대로
발행됐다 — "발행 전에 검토하고, 수정사항이 반영된 뒤 발행"이라는 운영자 요구와 정면 충돌.

## 결정 (Decision)
`publish-plan --due`가 발행 직전에 **열려 있는 `[수정요청·<채널key>]` 이슈를 조회**해
(`src/core/revision-gate.ts`), 걸린 콘텐츠를 ⛔ 보류한다. 수정이 반영되고 **이슈가 닫히면
(처리완료) 다음 사이클에 자동 발행**된다. 매칭 규칙은 대시보드 `openHolds()`와 CLI
`holdsForItem()`이 동일해야 한다:
- 본문 `(id: <planItemId>)` → 그 콘텐츠만 보류
- id 없음(채널 공통) → 그 채널의 발행 전 콘텐츠 전체 보류
- 본문 `업체: <clientId>` → 그 업체만 (없으면 전 업체 — 과거 이슈 호환, 공유 저장소 대비)

접수 즉시 guidance-sync의 `revision-note` 잡이 이슈에 "접수·발행 보류" 코멘트 + 텔레그램 푸시.
보류 알림은 항목당 1회 + **72시간마다 재알림**(`shouldNotifyHold`) — 스팸도, 조용히 잊히는
보류도 방지. `--id` 수동 발행은 운영자의 명시적 지시라 게이트 미적용.

## 고려한 대안 (Options)
- **A안(채택) — 발행 시점 이슈 직독 게이트**: 상태 저장 없음(이슈 open/closed가 곧 상태),
  대시보드·CLI가 같은 규칙으로 같은 소스를 읽음. 단점: 발행 시점 GitHub API 의존.
- **B안 — 이슈를 plan.json 상태(status=hold)로 동기화**: API 의존 제거. 단점: 동기화 워크플로
  추가·상태 이중화(이슈 닫힘과 plan 상태가 어긋나는 새 함정) → 배제.
- **C안 — 수정요청 오면 스케줄 자동 연기**: 예정시각 변경은 운영자 기획을 건드림 → 배제.

## 결과 (Consequences)
- (+) "검수 후 발행"이 사람 기억이 아니라 시스템으로 보장된다. 카드 `⛔ 발행 보류` 배지 +
  발행 대기 헤더 보류 카운트로 상태가 눈에 보인다.
- (+) 실패 안전: 이슈 조회 실패 시 그 사이클만 게이트 없이 진행(경고 로그) — 조회 장애로 발행이
  영구 정지되는 최악을 피함. 조회는 3페이지(300건)까지 페이지네이션.
- (−) 채널 공통 요청 1건이 그 채널 발행 전체를 세운다 — 의도된 보수성이지만, **이슈를 닫는 것을
  잊으면 채널이 계속 멈춘다**. 72시간 재알림이 안전망.
- (−) 워크플로 env에 `PSLAB_REPO`(=github.repository)와 `GITHUB_TOKEN` 필요 — 전용 인스턴스
  이식 시 누락하면 게이트가 대상 저장소를 잘못 보거나 레이트리밋에 걸린다.
- ⚠ 함정: 로컬(원격 세션)에서는 Node fetch가 프록시를 타지 않아 이슈 조회가 항상 실패한다
  ("게이트 없이 진행" 로그). CI에서는 정상 — 로컬 로그만 보고 게이트가 고장났다고 판단하지 말 것.
