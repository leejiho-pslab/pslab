# ADR-0007: dashboard.ts 템플릿리터럴 이스케이프 규약 + 배포 전 파싱검증

- **상태**: 채택됨
- **날짜**: 2026-07-16
- **관련 SKILL**: §6
- **관련 ADR**: —

## 맥락 (Context)
대시보드(`dashboard.ts`)는 브라우저에서 실행할 인라인 JS를 **TS 템플릿리터럴 문자열**로 emit
한다. 이때 정규식·따옴표 이스케이프가 **한 단계 풀리기** 때문에, 소스에 자연스럽게 쓴 코드가
브라우저에서만 깨진다. 실제로 `plainHead`의 `/\*/g`가 브라우저에서 `/*/g`로 풀려
"Invalid regular expression: missing /"로 **대시보드 전체가 오류 화면**이 된 사고가 있었다.
TS 컴파일·CI는 문자열 속 내용을 검사하지 않아 이 오류를 못 잡는다.

## 결정 (Decision)
템플릿리터럴로 emit되는 인라인 JS는 **한 단계 더 이스케이프**한다:
- onclick 등 따옴표는 `\\'`(백슬래시 2개) → 브라우저에 `\'`로 풀림.
- 정규식은 `/\\*/g`(백슬래시 2개) → 브라우저에 `/\*/g`로 풀림. (`/\*/g`로 쓰면 화면이 깨진다.)
- 가능하면 정규식을 피하고 **수동 루프**로 대체.
그리고 **대시보드 로직을 고치면 반드시** 로컬에서 `dashboard --out`으로 생성한 뒤 인라인
`<script>`를 **`vm.Script`로 파싱 검증**하고 배포한다(브라우저에서만 터지는 오류를 사전 차단).

## 고려한 대안 (Options)
- **A안(채택) — 이스케이프 규약 + vm.Script 파싱검증**: 저비용으로 브라우저 전용 오류를 사전 차단.
- **B안 — 인라인 JS를 별도 .js 파일로 분리**: 이스케이프 문제 근본 제거. 단점: 단일 HTML 자기완결성·
  Pages 배포 단순성이 깨짐(현 구조 대변경). 향후 리팩터 후보로 남김.

## 결과 (Consequences)
- (+) 화면 전체가 깨지는 배포 사고를 사전에 막는다.
- (−) 대시보드 인라인 JS를 고칠 때마다 이스케이프 주의 + 파싱검증 스텝이 필요.

## 관련 파일
`src/core/dashboard.ts`(인라인 `<script>`, plainHead 등)
