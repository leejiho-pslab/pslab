# ADR-0015: 캡컷 연동은 "드래프트 폴더 생성" 경로로 — 단, 파일럿 검증 후 채택

- **상태**: 제안됨 (Proposed) — 파일럿 검증 전까지 코드 없음
- **날짜**: 2026-07-31
- **관련 SKILL**: §8
- **관련 ADR**: ADR-0014(릴스 합성 엔진 Remotion)

## 맥락 (Context)

운영자 요청: **"이후에는 캡컷을 연결해서 (에이전트가) 직접 영상을 편집할 수 있도록 하자."**

Remotion 으로 자동 합성은 되지만, 그 결과물을 사람이 손보려면 지금은 방법이 없다.
영상은 완제품 mp4 로만 나오고, 편집 가능한 프로젝트 파일이 없다. 반대로 운영자가
캡컷에서 손본 감각(컷 타이밍·자막 위치)을 자동화 쪽으로 되먹일 길도 없다.

캡컷에는 **공개 편집 API 가 없다.** 사용할 수 있는 접점은 사실상 하나뿐이다 —
캡컷 데스크톱이 로컬에 저장하는 **드래프트 폴더**(`draft_content.json` / `draft_info.json` +
`assets/`)를 **직접 만들어 넣는 것**. 이 폴더를 캡컷이 인식하면, 앱을 열었을 때
"에이전트가 이미 편집해 둔 프로젝트"가 보인다.

이 방식을 쓰는 오픈소스가 이미 있다: [pyJianYingDraft](https://github.com/GuanYixuan/pyJianYingDraft)(중국판 剪映),
[pyCapCut](https://github.com/GuanYixuan/pyCapCut)(캡컷 국제판), [CapCutAPI](https://github.com/renqingfei/CapCutAPI),
[cutcli](https://docs.cutcli.com/). 스키마 정리본도 공개돼 있다
([draft_content.json 치트시트](https://gist.github.com/renezander030/80823f1d47081c312d2c1f9edd20dc22)).

## 결정 (Decision)

**타임라인 IR → 캡컷 드래프트 폴더 내보내기**를 연동 경로로 정한다.
ADR-0014 에서 IR 을 렌더러와 분리해 둔 이유가 이것이다 — 캡컷은 "또 하나의 렌더러"로 붙는다.

```
reel-scenes.json ─→ 타임라인 IR ─┬─→ Remotion  → mp4 (자동 발행용)
                                 └─→ 캡컷 드래프트 → 사람이 손편집 → (되먹임)
```

**단, 지금은 코드를 쓰지 않는다.** 아래 파일럿을 먼저 통과해야 채택으로 올린다.

1. 운영자 PC 의 캡컷 **버전과 드래프트 경로**를 확인한다.
2. 손으로 만든 릴스 프로젝트 하나를 열어 `draft_content.json` 이 **평문인지 암호화됐는지** 본다.
3. 평문이면 IR 4씬을 드래프트로 내보내 캡컷에서 열리는지 확인한다.

운영자용 절차서는 [`docs/캡컷-연동-가이드.md`](../../../../docs/캡컷-연동-가이드.md).

### 버전별 상황 (2026-05 커뮤니티 검증 기준, 직접 확인 필요)

| 제품 | 버전 | 드래프트 | 연동 |
|---|---|---|---|
| **캡컷 국제판** (CapCut) | 6.x ~ 9.x | 평문 JSON | 가능 |
| 중국판 剪映 (JianYing) | 5.9.0 | 평문 JSON | 가능 |
| 중국판 剪映 (JianYing) | 6.0+ | 암호화 blob | 불가 |

국제판은 최신 버전도 평문이라는 보고가 우세하다 — 파일럿이 통과할 가능성이 높다는 뜻.
**단 剪映 6.0+ 는 한 번 저장하면 평문으로 되돌릴 수 없으므로**, 확인은 반드시 연습용 프로젝트로 한다.

## 고려한 대안 (Options)

- **A안(제안) — 드래프트 폴더 직접 생성**
  에이전트가 만든 편집이 캡컷에서 **그대로 편집 가능한 상태**로 열린다. 운영자 요청에 정확히 맞는다.
  대신 비공식 포맷이라 캡컷 업데이트에 깨질 수 있다.
- **B안 — 소재만 넘기고 편집은 사람이**
  씬 클립·자막 PNG·폰트를 폴더로 묶어 주고 캡컷에서 처음부터 조립. 절대 안 깨지지만
  "에이전트가 직접 편집" 이 아니다. 요청을 만족하지 못한다.
- **C안 — 표준 교환 포맷(EDL/XML/AAF)**
  다른 편집기와는 통하지만 **캡컷 데스크톱이 이 포맷들을 가져오지 못한다**. 대상이 캡컷인 이상 무의미.
- **D안 — 캡컷 상용 API 제휴**
  공식 지원이라 안정적이나 파트너 계약이 필요하고, 제공 범위가 템플릿 기반 생성에 가까워
  "임의 타임라인 편집" 과는 결이 다르다. 규모가 커지면 재검토.

## 결과 (Consequences) — 채택될 경우

- (+) 에이전트가 만든 편집을 사람이 이어받을 수 있다. 자동화와 손편집이 한 타임라인에서 만난다.
- (+) 되먹임 경로가 생긴다 — 운영자가 캡컷에서 고친 타이밍을 다시 읽어 IR 기본값에 반영할 수 있다.
- (+) IR 이 이미 있어 추가 작업이 "IR → 드래프트 JSON 변환" 한 단계로 끝난다.
- (−) **비공식 포맷 의존.** 캡컷이 업데이트되면 깨질 수 있고, 예고 없이 깨진다.
  → 드래프트 생성은 **발행 파이프라인 밖**에 둔다. 깨져도 매일 도는 자동 발행은 멀쩡해야 한다.
- (−) **암호화 리스크.** 剪映 6+ 는 `draft_content.json` 을 암호화한다. 국제판은 아직 평문이지만
  같은 조치가 언제든 올 수 있다 — 그때 이 경로는 통째로 막힌다. 그래서 파일럿이 먼저고,
  후퇴안(B안)을 미리 정해 둔다.
- (−) 드래프트는 **로컬 파일**이다. CI(리눅스 러너)에서 만들어봐야 쓸 사람이 없다.
  운영자 PC 에서 도는 경로이거나, 폴더를 압축해 전달하는 형태여야 한다.
- (−) 언어가 갈린다. 성숙한 라이브러리는 Python 인데 파이프라인은 Node 다.
  파이썬 스크립트를 하나 두거나(cafe24-ops-status 선례 있음) JSON 을 직접 쓰는 선택이 필요하다.

- (−) **내보내기 제약.** 드래프트 생성 도구들이 "생성한 드래프트는 윈도우판 캡컷에서 내보내야 한다"고
  명시한다. 운영자가 맥을 쓴다면 파일럿에서 같이 확인해야 한다.
