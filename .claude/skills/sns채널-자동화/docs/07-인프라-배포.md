# 인프라 · 배포 (워크플로 · Pages · 비용)

목적: GitHub Actions 워크플로 구성, Pages 배포·저장소 visibility 관련 인프라 함정, 그리고 운영 비용의 단일 출처.

---

## 워크플로 (`.github/workflows/`)

- `pslab-cron.yml` — 무인 루프(기획·렌더·성과·대시보드) + Pages 배포.
- `pslab-publish-due.yml` — **예약 발행만** 매시간. 렌더·성과수집 없음.
- `pslab-publish.yml` — 단건 수동 발행(`workflow_dispatch`, `id` 지정).
- `pslab-reels.yml` — 릴스 합성(주간 + 수동).
- `pages-deploy.yml` — `docs/` 배포.

> ⚠️ **GitHub 의 `schedule` 은 정시를 지키지 않는다 — 발행은 "창"이 아니라 "빈도"로 지킨다.**
> 이 저장소에서 실제로 재보니 예정보다 **1.7~2.7시간** 밀렸다(08-02 19:44·20:02 / 08-01 19:44·20:00
> / 07-31 20:32·20:39 — 전부 18:00 예정 창). 크론 창을 발행 시각에 맞춰 늘려도 창 자체가 늦게 뜨니
> 소용이 없다. 해법은 **발행만 떼어낸 경량 워크플로를 매시간 도는 것**(`pslab-publish-due.yml`).
> 지연 상한이 "다음 창까지"에서 "1시간 + 스케줄러 지연"으로 줄어든다.
> 전제 조건이 있다 — **발행 원장(→ [../adr/0017-발행-원장-멱등성-분리.md](../adr/0017-발행-원장-멱등성-분리.md))이 있어야 시간당 실행이 안전하다.**
> 원장 없이 `plan.json` 상태만 믿고 하루 24회를 돌리면 상태가 한 번만 되돌아가도 중복 발행이 난다.
> 그리고 매시간 도는 워크플로는 **아무 일도 안 했을 때 아무것도 커밋하지 않아야 한다** —
> `git diff --quiet -- data/` 로 실제 발행 여부를 판정해 대시보드 재생성·커밋·Pages 배포를
> 전부 그 뒤에 건다. 안 그러면 Pages 가 하루 24번 재배포된다.
> 크론과는 `concurrency: pslab-autopilot` 을 공유해 같은 브랜치에 동시 push 하는 걸 막는다.

(지침 반영 워크플로 `guidance-sync.yml`은 [03-기획-지능.md](03-기획-지능.md), 키워드 수집 스텝은 같은 문서 참고.
잡별 `timeout-minutes`(cron 25분/publish 15분/sync 15분)는 [06-대시보드.md](06-대시보드.md) 안정성 수칙.)

> ⚠️ **느린 렌더는 아예 별도 워크플로로 뺀다.** 매일 반드시 성공해야 하는 건 "대시보드가
> 최신인가"이지 "영상이 오늘 새로 나왔나"가 아니다. 영상 합성처럼 시간이 크게 튀는 작업은
> `pslab-reels.yml`처럼 **전용 워크플로 + 주간 스케줄 + 수동 실행**으로 분리해, 거기서 아무리
> 오래 걸려도 대시보드 파이프라인이 영향을 받지 않게 한다. (단계 타임아웃만으로 버티려다
> 2026-08-01 에 두 번 같은 사고를 냈다.)
>
> ⚠️ **잡 타임아웃만으로는 부족하다 — 긴 단계에는 단계별 `timeout-minutes`를 따로 건다.**
> 한 단계가 잡 한도를 다 먹으면 GitHub는 그 뒤 단계를 전부 `skipped` 처리한다. 2026-08-01 크론에서
> 릴스 렌더가 18분을 쓰고 25분 한도에 걸리면서 **카드는 정상 렌더됐는데 대시보드 생성·커밋·Pages
> 배포가 통째로 건너뛰어져** 아무것도 반영되지 않았다. 증상이 "CI는 성공처럼 보이는데 사이트가
> 그대로"라 원인을 찾기 어렵다. 렌더·합성처럼 시간이 튀는 단계는 ①단계 `timeout-minutes`로 가두고
> ②`continue-on-error: true`로 폴백을 열어두어, **커밋·배포 단계가 반드시 실행되게** 한다.

## 배포·Pages 인프라 함정 (하드-원)

- **private 저장소 = 무료 플랜에서 Pages 꺼짐(404)**. public 유지(시크릿은 안전). visibility 바꾸면
  Pages Source가 None으로 초기화되니 다시 `GitHub Actions`로 켜야 함.
- **GITHUB_TOKEN으로 push하면 다른 워크플로가 트리거되지 않음**(무한루프 방지). 그래서 각 워크플로가
  자기 배포 스텝을 가져야 하고, **Pages 배포하는 워크플로는 concurrency group을 통일**(예: `pages`)해야
  동시배포 경쟁(→404)이 안 생긴다. 여러 프로젝트가 한 repo/Pages를 공유하면 특히 주의(업체별 저장소
  분리 원칙 → [01-도메인-데이터.md](01-도메인-데이터.md), [04-채널연동.md](04-채널연동.md)).
- **커밋 메시지에 `[skip ci]` 금지**(Pages 배포까지 막힘).
- **동시 push 충돌**: 커밋 스텝에 `git pull --rebase` + 재시도.

미디어를 반드시 CI에서 렌더/다운로드해야 하는 이유(개발환경 egress 제약)는 [02-콘텐츠-엔진.md](02-콘텐츠-엔진.md)와
[08-함정과-결정.md](08-함정과-결정.md). 시드 파일 강제 커밋 누락으로 CI가 조용히 렌더를 건너뛰는 함정은
[01-도메인-데이터.md](01-도메인-데이터.md).

## 배포 모드 (`deployMode`) — 업체별 변수

SKILL §0-1의 실행 상세. **코드·스킬은 동일**하고 데이터 위치·배포 대상만 달라진다.

| 모드 | 저장소 / 링크 | 세팅 |
|---|---|---|
| **`shared`** | 이 저장소 안 멀티클라이언트<br>`https://<owner>.github.io/<repo>/` | Settings→Pages→Source=**GitHub Actions**. 배포 워크플로 `concurrency: pages` 통일 |
| **`dedicated`** ⭐권장 | 업체 전용 public 저장소<br>`https://<owner>.github.io/<clientId>/` | 담당자가 `github.com/new`로 생성 → Settings→Secrets에 토큰 → Pages 켜기 |

- 업체가 2곳 이상이면 `dedicated`로 간다. **한 저장소에 몰아넣으면** Pages 배포 경쟁, 브랜치 파편화,
  발행물 링크 깨짐이 실제로 발생했다(하드-원).
- ⚠ Claude의 GitHub 통합이 기존 repo에만 스코프면 **새 repo 생성·푸시가 403**으로 막힌다.
  담당자가 저장소를 만들고 접근 권한을 부여(또는 `add_repo`)해야 코드를 올릴 수 있다.
- 고객에게 공유할 링크는 **로그인 없이 열리는 공개 주소**여야 한다(비공개 산출물 링크는 고객 화면에서
  로그인/404로 보인다 — 실제 사고).

### 전용 인스턴스(dedicated) 엔진 동기화 절차 — vittz 실증

허브(개발 브랜치)에서 엔진을 고치면 전용 인스턴스 저장소까지 **3단계**로 내보낸다
(vittz 기준 실증 경로 — 다른 dedicated 업체도 동일 패턴):

1. **허브 커밋** — 지정 개발 브랜치(예: `claude/vittz-…`)에 엔진·문서 변경을 커밋·푸시.
2. **미러 브랜치 동기화** — 허브 저장소의 `vittz-standalone` 브랜치(전용 저장소 main과 히스토리
   공유)를 워크트리로 체크아웃해 변경분을 적용·커밋·푸시.
   - ⚠ **통째 복사 금지**: standalone src가 허브 개발 브랜치보다 최신일 수 있다(허브 main에서
     받은 기능 보유). 반드시 `diff`로 확인 후 **변경분만 패치**. (dashboard.ts처럼 1:1 동기 파일은
     복사 가능, cli.ts처럼 갈라진 파일은 Edit로 패치.)
   - 허브 워크플로명(pslab-cron 등)과 인스턴스 워크플로명(vittz-cron 등)이 다르므로 워크플로
     수정은 파일명 매핑해서 반영.
   - standalone에서 `npm ci && npm run build` + 대시보드 재생성(`docs/index.html`) + 인라인 JS
     문법 검증까지 하고 커밋(대시보드 HTML은 인스턴스에선 커밋 대상).
3. **전용 저장소 배포** — 전용 저장소(예: `leejiho-pslab/vittz-sns`) 클론에서 허브 원격의
   `vittz-standalone`을 fetch → `merge --ff-only` → `main` 푸시. `pages-deploy`(docs/** 트리거)가
   자동 배포. **fast-forward가 안 되면 누가 전용 저장소에 직접 커밋한 것** — 그 커밋을 미러
   브랜치로 먼저 역동기화한 뒤 진행(강제 푸시 금지).

배포 직후 몇십 초는 Pages 아티팩트 교체로 **일시 404**가 날 수 있다(정상). 라이브 확인은
`curl -w "%{http_code}"` + 핵심 마커 grep으로.

## 세션의 외부 접근 = "환경의 네트워크 정책" (중요)

- **403/000이 나오면 사이트 고장이 아니라 정책 차단부터 의심**한다.
  확인: `curl -sS "$HTTPS_PROXY/__agentproxy/status"`
- 정책이 **열린 환경**이면 세션에서 직접 네이버·유튜브·인스타 접속이 가능하다.
- 정책이 **닫힌 환경**이면 기존 방식대로 **세션에서 생성 → URL 저장 → CI(GitHub Actions)에서 다운로드**.
  (미디어 파이프라인은 이 가정으로 설계돼 있다 → [02-콘텐츠-엔진.md](02-콘텐츠-엔진.md))

### 외부 사이트 열람·발행물 검수 — `scripts/site-view.mjs`

```
node scripts/site-view.mjs shot <url>        # 스크린샷
node scripts/site-view.mjs reel <릴스url>     # 인스타 릴스 mp4 + 3초 간격 프레임
```
- 릴스는 **embed 페이지가 로그인 없이 영상을 서빙**하는 점을 이용한다.
- ⚠ **크로미움을 직접 띄우지 말 것** — 프록시와 **TLS1.3 충돌**로 전 사이트 연결이 리셋된다.
  이 스크립트에 TLS1.2 강제 플래그(`--ssl-version-max=tls1.2 --disable-http2 --disable-quic`)가
  내장돼 있으니 **반드시 이걸 경유**한다.
- **유튜브 영상 다운로드(yt-dlp)는 데이터센터 IP 봇체크로 실패**한다. 메타데이터·실조회수·자막·댓글은
  YouTubeData MCP 도구로, 자사 영상 원본은 `docs/shorts/`에 있는 것을 쓴다.
- site-view `post` 모드(인스타 캐러셀 전 슬라이드 캡처)는 [06-대시보드.md](06-대시보드.md) 레퍼런스
  링크 인박스 학습에서 사용.

## 비용

- **거의 전부 무료**: GitHub Actions(무료 분), Pages(공개 repo), 렌더(Chromium/ffmpeg).

  힉스필드 영상(편당 ~10크레딧). 콘솔에서 사용 한도 걸어두면 초과 없음.
