# SNS 채널 자동화 (sns채널-자동화)

브랜드 하나의 SNS를 **무료로 24시간 무인 운영**하는 완성형 시스템. 이 파일은 **허브(라우터)**이고,
실제 지침은 `docs/NN-*.md`에, 결정 이유는 `adr/`에 **단일 출처**로 나뉘어 있다(§2 문서 지도).

> 핵심 철학: **대시보드가 곧 제품이다.** 모든 작업 결과는 대시보드(GitHub Pages)에서
> 링크로 확인 가능해야 한다. 비개발자 담당자를 위해 설명은 **쉬운 한국어**로.

> 🧠 **작업 시작 전 [`adr/README.md`](adr/README.md)(결정 기록 인덱스)와 관련 `docs/`를 먼저 확인**한다.
> 이 스킬은 **docs/(어떻게=지침) + adr/(왜=결정 이력)** 2계층으로 기억을 유지한다. 중요한 결정·
> 반복 함정을 발견하면 **ADR을 추가**하고 달라진 절차는 해당 `docs/` 문서에 반영한다.

## §0 클라이언트 변수 계약 (업체마다 달라지는 것 — 여기만 바꾼다)

이 스킬은 **업체 중립(client-agnostic)**이다. 코드·스크립트·문서는 모든 업체가 공유하고,
**업체별 차이는 아래 변수로만** 표현한다.

> ⛔ **업체명을 코드·문서 본문에 하드코딩하지 말 것.** 항상 `<clientId>` 같은 변수로 쓴다.
> 문서에 등장하는 실제 업체명은 **"이 방식이 검증된 출처" 표기이거나 `예:` 예시**일 뿐이며,
> 지침 자체는 항상 일반형이어야 한다. (예: `PSLAB_*` 접두어는 업체명이 아니라 **시스템
> 네임스페이스**다 — 전용 저장소로 분리하면 `<CLIENT>_*`로 바뀐다.)

| # | 변수 | 단일 출처(위치) | 예시 값 | 이걸 바꾸면 달라지는 것 |
|---|---|---|---|---|
| 1 | **`<clientId>`** | `clients/<id>.json` 파일명 | `demo-cafe`, `pslab` | 모든 데이터·산출물 경로(`data/clients/<id>/`, `docs/cards/<id>/`) |
| 2 | **브랜드 정체성** | `data/clients/<id>/brand-brief.json` | 분석·방향성·감도 3종 | AI 프롬프트 최상단 — 글의 톤·소재 성향 |
| 3 | **운영자 지시** | `design.json` → `humanNotes` | "로고 더 크게" | 프롬프트 **최우선**. AI가 지우지 못함(사람 지시 우선) |
| 4 | **디자인 토큰** | `data/clients/<id>/design-tokens.json` | 색·폰트·레이아웃 | 카드·블로그 이미지 렌더 결과 (**코드 수정 없이** 디자인 변경) |
| 5 | **채널 구성** | `clients/<id>.json` → `accounts`, `channelLinks` | IG·스레드·블로거·유튜브… | 발행 대상 채널 + 대시보드 "채널 바로가기" |
| 6 | **채널별 가이드** | `data/clients/<id>/channel-guides.json` | 주제 풀·핵심 가이드 | 소재 선정 우선순위(`favoredTopics`·리서치 키워드) |
| 7 | **발행 스케줄** | `clients/<id>.json` → `scheduleTimes` | `18:00` KST | cron 배치 시각·빈도 |
| 8 | **시크릿 접두어** | GitHub Secrets 이름 | `PSLAB_*` / `<CLIENT>_*` | 채널 토큰 주입 |
| 9 | **배포 모드** | `clients/<id>.json` → `deployMode` | `shared` \| `dedicated` | 저장소·Pages 주소·워크플로 배치 (§0-1) |
| 10 | **발행 스위치** | Variables `<PREFIX>_DRY_RUN` | `true`(기본=안전) | 시뮬레이션 / 실제 발행 |
| 11 | **드라이브 레퍼런스·지침** | 드라이브 `※alway on/<n>. <업체>/` + `data/clients/<id>/design-reference.json`(폴더 ID·학습 결과) | `※alway on/2. 비츠` | **기획·제작 전 필수 참조** — 채널별 레퍼런스·지침이 감도·지시의 1순위 출처 ([docs/02](docs/02-콘텐츠-엔진.md)) |

**운영 규칙**
- 새 업체 추가 = **위 11개를 채우는 일**. `src/`·`scripts/` 코드는 건드리지 않는다.
- 코드가 업체별로 갈라져야 할 것 같으면 → **변수로 승격**해 이 표에 추가한다(코드 분기 금지).
- 업체 데이터는 서로 **격리**한다 → [docs/01-도메인-데이터.md](docs/01-도메인-데이터.md) 멀티클라이언트 격리 원칙.
- `data/clients/**`는 gitignore이므로 시드 파일은 **`git add -f` 필수**(안 하면 CI가 조용히 렌더를 건너뛰고
  다운로드 링크가 404로 깨진다).
- 변수 스키마의 실제 필드·기본값은 [docs/01-도메인-데이터.md](docs/01-도메인-데이터.md)가 단일 출처다.

### §0-1 배포 모드 (`deployMode`) — 저장소 위치도 변수다

| 모드 | 언제 쓰나 | 저장소 / 링크 | 주의 |
|---|---|---|---|
| **`shared`** | 업체 1~2곳·빠른 시작 | 이 저장소 안에서 멀티클라이언트<br>`https://<owner>.github.io/<repo>/` | 업체가 늘면 **Pages 배포 경쟁·브랜치 파편화**가 생긴다 → 배포 워크플로 `concurrency: pages` 통일 필수 |
| **`dedicated`** ⭐권장 | 업체 2곳 이상·독립 운영 | 업체 전용 **public** 저장소<br>`https://<owner>.github.io/<clientId>/` | 담당자가 `github.com/new`로 직접 생성. Claude 통합이 기존 repo에만 스코프면 새 repo 푸시가 403 → 접근 권한 부여(또는 `add_repo`) 필요 |

두 모드에서 **코드·스킬은 완전히 동일**하고, 달라지는 것은 **데이터 위치와 배포 대상**뿐이다.
상세·함정 → [docs/07-인프라-배포.md](docs/07-인프라-배포.md).

## §1 표준 진행 순서 (기본 실행 계약 · 반드시 이 순서로)

> **신규 업체 요청("○○ SNS 자동화 세팅해줘")을 받으면 아래 7단계를 순서대로 밟는다.** 각 단계 끝에는
> **검수 게이트(🚦)**가 있어 담당자 승인 전에는 다음으로 넘어가지 않는다. **절대 앞질러 콘텐츠를 대량
> 생성하지 말 것** — 콘텐츠 생성(⑥)은 ④ 채널 전략과 ⑤ 기획 검수가 끝난 뒤에만.

1. **브랜드 정의·분석** — `clients/<id>.json` + `brand-brief.json` 초안 → 🚦 브랜드 정의 승인.
2. **대시보드 뼈대만** — `design.json` + 빈 `plan.json`, 대시보드 뜨는 것까지만 → 🚦 링크 열림.
3. **채널 계정 연결** — 토큰 발급 → GitHub Secrets, `check-tokens` 점검 → 🚦 연결됨 확인.
4. **채널별 운영 전략 정의** — 포맷·주제·빈도를 지침(`channel-guides.json`)에 반영 → 🚦 전략 승인.
5. **콘텐츠 기획→검수** — **먼저 드라이브 레퍼런스·지침 열람(§0 변수 #11, 필수)** →
   기획안(`plan.json` status=planned) 생성·검수 → 🚦 기획 검수 통과.
6. **콘텐츠 15일치 생성** — **드라이브 레퍼런스·지침 재확인 후** 검수 통과 채널만 렌더/합성,
   `schedule-daily`로 배치 → 🚦 내용 체크.
7. **자동화 ON + 텔레그램** — `<PREFIX>_DRY_RUN=false` + 텔레그램 연결 → 🚦 첫 발행·수신 확인.

각 단계 시작 시 몇 단계인지 한 줄로 알리고, 끝나면 산출물 링크 + 다음 예고 + 게이트 질문으로 마무리한다.
**7단계 전체의 상세(산출물·명령어·게이트 기준)는 [docs/00-개요와-온보딩.md](docs/00-개요와-온보딩.md).**

## §3 결정 기록(ADR) · 기억 시스템 (요약)

이 스킬은 **docs/(어떻게=지침) + [`adr/`](adr/README.md)(왜=결정 이력)** 2계층으로 스스로 기억·갱신한다.
작업 시작 시 `adr/README.md` 인덱스를 읽어 관련 ADR을 확인하고, **되돌리기 어려운 결정은 다시 논쟁하지
않는다**. 중요한 결정·반복 함정을 만나면 `adr/template.md`로 **새 ADR을 추가**하고, 달라진 절차는 해당
`docs/` 문서에 반영하며, 코드·문서·ADR을 **한 커밋**으로 묶는다.

- 병렬 브랜치에서 스킬이 갈라졌으면 → [ADR-0010 병렬브랜치 통합정책](adr/0010-병렬브랜치-통합정책.md)
  절차(충돌 집계 → replay 통합 → 스냅샷 최신성 확인)를 따른다.
- 이 스킬을 하나로 합치고 업체 차이를 변수로 뺀 결정 → [ADR-0013](adr/0013-스킬-통합-클라이언트-변수화.md).

상세 규약·기준·인덱스는 [adr/README.md](adr/README.md).
